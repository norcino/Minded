Business logic drowns in plumbing

Every endpoint re-implements the same cross-cutting concerns, slightly differently each time.

~7%

of a typical endpoint is the actual use case. The rest is plumbing that every engineer rewrites.

Duplicated

The Minded idea

Describe the use case. The pipeline does the rest.

Callers send a message. Opt-in layers wrap the handler. The response flows back out the same way.

You write

A command or query, its handler, and optionally a validator. Plain classes, constructor DI.

You declare

Behaviour as attributes: [ValidateCommand], [MemoryCache], [RequirePermissions].

Minded wires

Handler discovery, the decorator chain and HTTP mapping, all registered in one place.

02 · How Minded works

Three patterns, one pipeline

Each pattern removes one kind of coupling. Together they leave the handler with nothing but the use case.

Mediator

One entry point: IMediator. Callers send messages and never know who handles them.

  • Controllers stay thin
  • No handler-to-handler coupling
  • Handlers resolved from DI, invocation cached

CQRS

Commands change state. Queries read it. Never both in the same message.

  • Intent visible from the type name
  • Each side gets its own decorators
  • Reads and writes evolve independently

Decorator

Cross-cutting behaviour wraps the handler in layers. Each layer does one thing.

  • Add behaviour without editing handlers
  • Write once, apply everywhere
  • Opt-in per message via attributes

02 · How Minded works

The decorator onion

Each layer has one job. Registration order decides who wraps whom.

Execution order

Exception→ Logging→ Retry→ Validation→ Handler
Rule of thumb. First registered = innermost, last registered = outermost. Exception handling goes last so it sees every failure, including those raised by other decorators.
Why it matters. Order is a design decision you make once, in one file, instead of in every endpoint.

02 · How Minded works

Anatomy of a feature

Small files with one job each. The command reads like a spec; the handler is just the use case.

Application.Category/
├─ Command/
│   └─ CreateCategoryCommand
├─ CommandHandler/
│   └─ CreateCategoryCommandHandler
├─ Validator/
│   └─ CreateCategoryCommandValidator
├─ Query/
│   └─ GetCategoryByIdQuery
└─ QueryHandler/
    └─ GetCategoryByIdQueryHandler
  • Message: data + declared behaviour. Immutable after construction.
  • Handler: the business action only. No validation, no try/catch, no logging.
  • Validator: rules, discovered automatically.

03 · Principles built in

SOLID, by construction

Each letter maps to something concrete in the framework, not to a guideline you hope people follow.

S

Single responsibility

One handler per use case. Validators validate. Each decorator owns one concern. Controllers only route.

CreateXHandler
O

Open / closed

Add behaviour by registering a decorator or adding an attribute. Existing handlers stay untouched.

Every decorator is an ICommandHandler<T>. The mediator can't tell a decorated handler from a bare one.

Interface segregation

Small, opt-in contracts. A message implements only what it needs.

Clean Architecture without the ceremony

Dependencies point inward. The web layer and the database are details that plug into the application layer.

03 · Principles built in · Separation of concerns · KISS · YAGNI

Pay only for what you use

A small core and opt-in extensions. Nothing runs unless you ask for it.

Framework · the core

CQRS.AbstractionsCQRSMediator.Abstractions MediatorDecorator

Extensions · pick what you need

Configuration WebApi Validation Exception Logging DataProtection Retry Caching.Memory Transaction Authorization Context

Validation, Caching and DataProtection also ship .Abstractions packages, so libraries can depend on contracts only.

KISS. Handlers are plain classes with constructor injection. No base class to inherit, no framework types in your domain logic beyond the message contracts.

Opt-in, level 1: the application

Install the package and register the decorator once in AddMinded(...). Not registered means not running.

Opt-in, level 2: the message

Add the attribute to the command or query that needs it. Without it the decorator simply passes the call through; Validation and Retry aren't even added to that handler's chain.

YAGNI

Start with Mediator + Validation + Exception. Add caching, retry or transactions when a real need shows up, without rewriting a single handler.

03 · Principles built in · Declarative policy · Fail fast

Policy lives next to the use case

Open a command and you see everything that will happen to it. Real examples from the Example application.

Fail fast. Misconfiguration surfaces when the app boots, not in production: invalid authorization attributes are rejected at startup, and a [MemoryCache] query without IGenerateCacheKey fails startup in Debug builds.
  • ① Cached for 5 minutes, keyed by the query.
  • ② Claim check: global admins don't use tenant data.
  • ③ Resource check: the category must belong to the caller's tenant.
  • ④ Validated by its ICommandValidator before the handler runs.
  • ⑤ Retried on transient failure, because the update is idempotent.
  • ⑥ Permission required, checked with a compile-time constant.

Reviewers check behaviour by reading attributes, not by tracing through layers of service code.

04 · Built to last

Production-ready details, included

The safeguards most teams only add after their first production incident are already in place.

Cancellation

CancellationToken flows through every layer. Cancelled requests return 499 and log as Information.

Correlation

Every message has a TraceId. Context propagates it to nested calls.

Fail fast

Decorator attributes are validated at startup, before the first request.

Runtime switches

Options have *Provider counterparts for feature flags. No redeploy.

Privacy

[SensitiveData] keeps PII out of logs and exception context.

Low overhead

Handler types and compiled invocation delegates are cached. Validation and Retry aren't even added to handlers whose message lacks their attribute.

Compatible

Built for net10.0, with a netstandard2.0 build for libraries. Signed assemblies, SourceLink, symbol packages.

Reference app

ASP.NET Core API + React front end: RBAC, multi-tenancy, OData, live log streaming.

05 · Decorator catalogue

Putting it together: a recommended pipeline

Execution order, outermost first. Every position has a reason.

Commands

Context→Exception→ Logging→Authorization→ Retry→Transaction→ Validation→Handler

Queries

Context→Exception→ Logging→Authorization→ Caching→Validation→Handler

Context outermost

Every layer, including nested calls, sees the same ambient context and TraceId.

Auth before cache

Permissions are checked even when the answer comes from the cache.

Retry around transaction

Each attempt gets a fresh transaction instead of reusing a failed one.

Validation innermost

Database-backed rules read inside the same transaction as the write.

Decorator 1 / 9

Validation

Reject bad input before it reaches the handler, with structured, field-level feedback.

Minded.Extensions.Validation[ValidateCommand][ValidateQuery]CommandsQueries
  • Opt-in per message. No attribute, no validation overhead.
  • Validators are plain DI classes, discovered automatically.
  • Reusable entity validators (IValidator<TEntity>) shared across commands.
  • Errors carry property, message, severity and error code.
Placement. Innermost, so rules that read the database run inside the transaction.

Decorator 2 / 9

Exception

One place for unhandled errors. No try/catch in handlers or controllers.

Minded.Extensions.ExceptionExceptionOptionsSerializeProviderCommandsQueries
  • Outermost behavioural layer: catches failures from every decorator below it.
  • Logs the failing command or query with its data, after sanitization.
  • Non-serializable members (tokens, streams, delegates) and [SensitiveData] are stripped.
  • Wraps errors in CommandHandlerException<T> / QueryHandlerException<T,R>.
Runtime control. Decide per environment, or per flag, whether message data is serialized into error logs.

Logging

Decorator 4 / 9 · companion to Logging & Exception

Data Protection

Mark a property once. It stays out of every log and exception dump, everywhere.

Minded.Extensions.DataProtection[SensitiveData]ShowSensitiveDataProviderGDPR / CCPA
  • Applied automatically by Logging and Exception once AddDataProtection() is configured.
  • Hidden by default; reveal only in development or behind a flag.
  • Recursive with guards: max depth 3, collections truncated to 10 items.
  • Extensible with custom IDataSanitizer or ILoggingSanitizer.
Privacy as a type-level decision. Reviewers look for one attribute, not for every log statement that might leak.

Decorator 5 / 9

Retry

Ride out transient failures with declarative backoff, instead of hand-rolled loops.

Minded.Extensions.Retry[RetryCommand][RetryQuery]idempotent operations onlyCommandsQueries
  • Up to 5 delay values for exponential backoff; the last delay is reused.
  • A bare attribute uses defaults from RetryOptions, appsettings or providers.
  • ApplyToAllQueries: reads can retry without any attribute.
  • Every attempt is logged with exception details.
Placement. Wrap it around Transaction so each attempt runs in a fresh transaction.

Decorator 6 / 9

Caching

Serve repeat reads from memory, with the cache policy declared on the query itself.

Minded.Extensions.Caching.Memory[MemoryCache]IGenerateCacheKeyIGlobalCacheKeyPrefixProviderQueries
  • [MemoryCache] and IGenerateCacheKey go together; checked at startup in Debug.
  • Absolute, sliding or fixed-date expiration per query.
  • Failures are never cached, so the next call tries again.
  • Cache faults degrade to a normal query unless FailOnError = true.
Placement. Inside Authorization, so cached answers are still permission-checked.

Decorator 7 / 9

Transaction

All-or-nothing database work, including nested commands, with one attribute.

Minded.Extensions.Transaction[TransactionalCommand][TransactionalQuery]TransactionScopeCommandsQueries
  • Nested commands and queries join the ambient transaction automatically.
  • Per-message IsolationLevel and TimeoutSeconds.
  • Rolls back on exceptions and, by default, on unsuccessful responses.
  • Database only: HTTP calls, queues and e-mails need outbox or saga patterns.
Business rules can roll back too. Return Successful = false and the work is undone.

Decorator 8 / 9 · part 1: roles, permissions, claims

Authorization

Declarative access control on the message, enforced for every caller: HTTP, workers and nested calls alike.

Minded.Extensions.AuthorizationIAuthorizationContextAccessorAuthorizationOptionsCommandsQueries
[RequireAuthentication] any signed-in caller [AllowUnauthenticated] explicit public [RequireRoles] role names [RequirePermissions] permission names [RequireClaim] claim value or property match [RequireResourceAccess] next slide

Match modes All · Any · AtLeast · None. Attributes combine with AND; OrAnyRole / OrAnyPermission / OrAnyClaim add escape hatches.

Checked at startup. Rules are compiled once and cached; contradictory attributes fail on boot.

Decorator 8 / 9 · part 2: resource-based access

Authorization: can this caller touch this resource?

The policy is itself a query, dispatched through the mediator. Testable, reusable and tenant-aware.

Minded.Extensions.Authorization[RequireResourceAccess]IQuery<bool>requires Context
  • Resource id comes from a message property; caller id from a claim.
  • The authorization query is a normal query: unit test it, reuse it.
  • Startup checks that the property exists and the query has a (object resourceId, string claimValue) constructor.
  • Short-circuit with OrAnyRole, e.g. for administrators.
Multi-tenancy, declared. Tenant isolation lives on the query instead of in every handler.

Decorator 9 / 9

Context

One ambient context per root call, shared by every decorator and handler, including nested calls.

Minded.Extensions.ContextIMindedContextAccessorITraceableAsyncLocalCommandsQueries
  • TraceId seeded from the root ITraceable message and propagated to nested ones.
  • Share work: a validator loads an entity once; the handler reuses it.
  • BeginScope<T>: flow-scoped flags, invisible to parallel branches.
  • Current is never null; outside a call it's a no-op context.
Foundation for other decorators. Resource-based authorization uses it to prevent recursion.
